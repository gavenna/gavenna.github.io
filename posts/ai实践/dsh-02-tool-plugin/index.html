dsh 系列第 2 篇：插件开发实战。第 1 篇摸清了 dsh 的源码地形图，本篇把它变成真东西——两个工具插件。

从地形图到真插件
#

地形图的结论是：“加能力用插件（副作用注册，卸载自动回收）"。但读懂了和做出来之间，隔着挂载机制、包形态、验证手段三道坎。我的策略是分三步走，每步都有明确验收：

  1. 试跑（30 分钟）：做一个最小工具插件，验证我对插件契约和挂载机制的理解——挂上去、在当前会话里被模型真实调用一次，才算数；
  2. 核心：做正式插件的逻辑核心——四检查器，纯函数、可单测，13/13 测试全绿；
  3. 接线挂载：把核心接成工具、挂到 web profile（live 热更）、端到端验证 + 发布形态收尾。

第一个插件叫 probe-hello（探测），第二个叫 dsh-health-check（体检）。名字就说明了定位：一个验证"路通不通”，一个真正干活。

第一步：probe-hello，30 分钟的最小插件
#

规格极简：注册一个工具 dsh_whoami，无参数，返回运行环境摘要 { time, cwd, platform, nodeVersion }，面向模型渲染成一行文本。零第三方运行时依赖。

不 import 任何东西的插件
#

dsh 的官方示例用 defineTool 封装工具定义。但 probe-hello 刻意不 import 它——因为 defineTool 返回的就是一个普通对象（ToolDefinition），我直接手写这个形状，插件就对 @deepseek-ai/* 零运行时依赖。模块只 import 空气，全靠 apply(ctx) 拿到的 ctx 和 Node 全局：

export const name = 'probe-hello'      // 插件显示名(loader 诊断用)
export const inject = ['tools']        // 等工具注册表就绪再 apply

export function apply(ctx) {
  ctx.tools.register({
    name: 'dsh_whoami',
    description: 'Report a summary of the current runtime environment: …',
    parameters: { type: 'object', properties: {} },   // 手写 JSON Schema
    output: {
      schema: { … },                                   // canonical 结构化输出
      render: (_args, value) => [{                     // 模型看到的一行摘要
        type: 'text',
        text: `[whoami] ${value.time} cwd=${value.cwd} platform=${value.platform} node=${value.nodeVersion}`,
      }],
    },
    async execute() {
      return { time: new Date().toISOString(), cwd: process.cwd(),
               platform: process.platform, nodeVersion: process.version }
    },
  })
}

插件导出契约就三个字段：name（显示名）、inject（依赖的服务，等就绪再 apply）、apply（注册能力）。ctx.tools.register 的注册是 cordis fiber 上的 effect——插件被卸载（包括 live 热更重载）时自动注销，零手写 dispose。

file:// 直挂 + live 热更
#

挂载方式是整个试跑里最有信息量的一步。dsh 的 profile 用户层补丁支持两种引用插件的方式：包名（Node 从 profile 的 node_modules 解析）或绝对 file:// URL。跨盘路径（我的插件在 D 盘、dsh 装在别处）用相对 specifier 够不到，所以直挂文件 URL：

# ~/.dsh/profiles/web/cordis.patch.yml (追加)
- insert:
    - id: probe-hello
      name: 'file:///D:/dsh-playground/probe-hello/src/index.mjs'

web profile 是 patchReload: live——文件一改，watcher 重放补丁树。改完即生效，不用重启。挂载的验证方式也最直接：在正在跑的 dsh Web 会话里直接调一次 dsh_whoami，看模型能不能拿到那一行 [whoami] … cwd=… platform=win32 node=v24.15.0。能，就证明整条链路（插件契约 → 挂载 → 热更 → 工具注册 → 模型可见 → 真实调用）全通。

第二步：dsh-health-check，正式插件的三个架构决策
#

试跑证明了"路通"，接下来做真正有用的东西。dsh-health-check 的定位是：安装/升级 dsh 后跑一次体检——版本环境、子包 .bin 链接完整性、配置树摘要、端口状态。这四项是我此前手动排障 dsh 时反复做的手工检查，把它自动化成插件。

写正式包前定了三个硬决策，事后看都值回了票价：

决策一：纯 ESM、零构建、零运行时依赖
#

.js 源码 + JSDoc 类型，不引入 TypeScript 编译链（tsc/tsdown），没有 prepare 脚本。理由有二：

  • probe-hello 已实证 file:// URL 直挂能加载纯 JS 插件，构建不是必需品；
  • 没有 prepare 脚本，意味着 npm 安装和 git 安装都不需要构建授权——官方发布文档里坑最多的就是 prepare 脚本在安装时跑构建。对发布到 npm 的包，这是实打实少一类故障。

devDependencies 只有 vitest（测试用）；dependencies 必须为空。包出口 exports: { ".": "./src/index.js" }。

决策二：检查器 = 参数化纯函数，所有 I/O 走注入
#

这是整个包最重要的架构决策。四个检查器各自是一个 (inputs, io) => Promise<CheckResult> 的纯函数，禁止直接 import node:fs / child_process——所有读写文件、探测端口、跑命令的能力都经注入的 io 对象：

// 每个检查器长这样:逻辑内不碰任何真实 I/O
async function checkVersion({ pkgPath }, io) {
  const pkg = await io.readJson(pkgPath)     // 读不到/解析失败 → fail
  return { name: 'version', status: 'ok',
           summary: `${pkg.name}@${pkg.version}`, detail: … }
}

单测因此变得极其干净：注入假 io（stub），测试就完全不需要碰真实文件、真实端口、真实 dsh。13 个用例全绿，覆盖每检查器的 ok/fail/warn/skip 分支、enabled 过滤、输出顺序：

// port 检查的测试:注入返回 true 的假探针 → 期望 warn
// (端口被占不一定是坏事——服务可能本来就在跑)
const results = await checkPort({ expectedPort: 3080 },
                { tcpProbe: async () => true })
// → status === 'warn', detail 提示 Hyper-V 保留区间换端口

状态语义也值得一说：port 被占是 warn 不是 fail——“端口被占"可能是服务正常在跑，也可能是跟 Windows Hyper-V 保留端口区间撞了，检查器只报告事实和换端口的建议，不武断判死。config-dump 检查跑 dsh --dump-config 失败时判 skip 而不是 fail——环境里没有 dsh 可执行文件是正常态，不该算故障。只有 version 读不到、.bin 链接缺失这种"装坏了"才是 fail。

决策三：工具参数面保持最小，路径不许硬编码魔法值
#

工具 dsh_health_check 的参数只有两个且全部可选：checks（要跑的检查子集，省略=全跑）和 expectedPort（默认 3080）。dsh 仓库路径不进参数面，而是运行时解析：优先 DSH_REPO 环境变量，未设则从当前 dsh 进程的工作目录推断，仍找不到就 skip 并在 detail 里说明——绝不在代码里写死一条路径。

工具输出是 canonical 值 + 面向模型的文本渲染两层：canonical 是 { summary, results: [...] }（结构化，可被程序消费），render 把它压成逐行文本（模型看到的样子）：

[health] 4 check(s): 3 ok, 1 warn
  [version] ok — @deepseek-ai/dsh-root@0.1.3-alpha.1
  [bin-links] ok — dsh bin links present in 2 package(s)
  [config-dump] ok — 525 lines, 20 bundle layer(s)
  [port] warn — port 3080 is already listening

（上面是我在本地用真实只读 I/O 跑 demo 的真实输出——config-dump 离线渲染出 20 个 bundle 层 149 条顶层条目、525 行；3080 被占 warn 是因为当时 dsh 正跑着。全程零 LLM 调用、零写入。）

第三步：接线、挂载与发布形态
#

逻辑核心验证完后，接线是薄薄一层：插件入口 apply 里注册 dsh_health_check，把工具参数映射成 runChecks 的 inputs，结果统计成 summary。这层刻意保持"薄”——可测的逻辑全在纯函数核心，接线只做参数翻译。

挂载用的是正式形态而不是 file:// 直挂：包内带一份 bundle 层声明，发布后用户一条命令安装：

# cordis.patch.yml — 按包名注册,由安装 profile 的 node_modules 解析(pnpm 管理)
- insert:
    - id: dsh-health-check
      name: dsh-health-check

// package.json 里声明 bundle 层位置
"dsh": { "bundle": { "patch": "./cordis.patch.yml" } },
"files": ["src", "cordis.patch.yml"]   // npm 只发这两个

发布形态收尾还包括：MIT LICENSE、能力面 README、pnpm pack 核验包里文件齐全。到此这个包就站在了"可发布"的门口——pnpm test 全绿、零运行时依赖、无构建步骤、安装即用。

三层递进：机制、逻辑、接线分开验证
#

回看整个开发过程，最有价值的不是代码，是验证策略的分层：

层验证什么手段
probe-hello插件契约 + 挂载 + 热更机制通不通真实挂载，会话内调用一次
纯函数核心检查逻辑对不对注入 stub io，13/13 单测，不碰真实环境
工具接线参数映射与输出形态薄层 + 真实只读 demo

这个分层让我在每一步都只用"够用"的验证：试跑不写测试（机制验证靠真实调用）；核心不跑真实 dsh（逻辑验证靠注入）；接线不做重测试（它太薄，风险在核心已消化）。把 I/O 赶到边缘、逻辑留在纯函数——这个模式还带来一个意外收益：它让 AI 写的代码变得可测试。写代码的人（不管是你还是 agent）只要遵守"I/O 全走注入"的约定，产出的核心就能被单测完整覆盖。这在本系列番外篇会展开讲。
