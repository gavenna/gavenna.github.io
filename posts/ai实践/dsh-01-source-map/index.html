dsh 系列第 1 篇：源码摸底。这个系列记录我以「定制 deepseek-harness」为路径系统学习一个 agent 框架源码的完整过程： ① 源码摸底（本文）→ ② 工具插件开发实战 → ③ mock LLM 无 key 验证 → ④ 主题适配与开源合规 → ⑤ Tauri 桌面壳。番外篇讲驱动这一切的「任务书」协作方法论。

起因：想定制，先看懂
#

我在深度使用 DeepSeek Harness（下称 dsh，deepseek-ai 开源的个人 agent 框架，Web / headless / 桌面形态都有）之后，冒出了定制它的念头：加自己的工具、改默认行为、甚至给它换皮肤、包桌面壳。但翻官方文档时总有一种"隔靴搔痒"感——文档告诉你能做什么，不告诉你为什么能、卡在哪。等真动起手来，八成要踩文档没写的坑。

所以我把目标定成一句话：系统性读懂 dsh 源码，直到"能不看文档画出 pnpm dsh web 从输入到工具被模型调用的完整链路"。这是这个系列一切后续工作的地基。

摸底方法：按启动链路走读，不从头翻到尾
#

一个陌生框架的源码，最忌讳从头到尾逐行读——你会在无关细节里淹死。我的做法是按启动链路走读：

  1. 先立环境基线：仓库能不能跑？pnpm dsh --version 是什么？有哪些 profile？默认配置长什么样？
  2. 沿一条主线走：CLI 入口 → profile 装配与 patch 应用 → 工具注册 → 插件副作用与热更 → 会话存储 → 验证闭环。主线就是 dsh web 从敲下回车到界面出来的路。
  3. 每站三步：grep 定位权威文件 → 精读实现 → 动手实证（跑命令、做实验验证读码结论）。
  4. 结论落盘：每个摸点写成带 路径:行号 证据的笔记，最后合并成一张「地形图」。

仓库约束：D:\agent-deepseek（0.1.3-alpha.1）只读——它是浅克隆，供上游更新用，任何摸底都不得改它；产物全部落在我自己的练手目录。

为什么强调实证？因为读码结论会骗人。后面会看到：--dump-config 看起来能代表"真实配置"，实际上它和真实启动之间有整整一道 schema 校验的鸿沟——这种坑，光读代码是发现不了的。

地形图主干：pnpm dsh web 的一次完整旅程
#

摸底最重要的产出是一张 ASCII 链路图，把 20 多个包、5 层配置、3 条热更路径压缩成一页。简化版长这样：

pnpm dsh web --no-open
 │  ("dsh" = node --import tsx/esm apps/cli/src/bin.ts —— tsx 直跑 TS 源码)
 ▼
bin.ts:24         薄分发器:parseDshArgs → 按 mode 动态 import runner
 │  web 不是子命令:commander 硬编码 alias → profile='web'
 ▼
profile-boot.ts   runProfile():
 ├─ 分层装配: bundle → 用户层 → home 层 → --patch overlay → telemetry
 ├─ boot() 挂 cordis 插件树(空根 cordis.yml + 整叠 patch)
 └─ patchReload==='live' → watchUserPatches(热更 watcher)
 ▼
cordis 树内       loader 按 patch 逐行挂插件 → 插件 apply(ctx, config)
 │  [例:tool-fs]  ctx.tools.register(defineTool({...}))  ← 副作用注册
 ▼
每个 model step  systemPrompt.assemble() → tools wireSchemas()
 │  → schemaOf 白名单:只投 name/description/parameters 给模型
 ▼
llm.stream(request) → 会话落盘 JSONL 批写(fsync, ≤200ms)
   → ~/.dsh/sessions/<projectKey>/<enc>/session.vN.jsonl.zstd

链路里最颠覆我直觉的几个点：

1. web 根本不是子命令。 commander 里一个硬编码 alias，解析出来就是 profile='web'，复用同一套 profile boot 通道。真正让 web 模式"是 web"的，是 profile 声明里的 bundles = [base, web-app] + patchReload = live。开箱的 5 档 profile（web / headless / acp / sdk / sdk-minimal）全是"包组合"差异，不是代码差异——这让"组合新 profile"变得极便宜：列两个 bundle 名而已。

2. dsh 的本质是"分层 patch 组装的 cordis 插件树"。 根 cordis.yml 是空的，每次启动重写；真正的插件清单是5 层 patch 叠出来的，应用顺序：

bundle 补丁(框架自带) → profile 用户层 → $DSH_HOME home 层 → --patch 覆盖层 → telemetry

后层按行命中覆盖前层。所以"改 dsh 配置"这个动作，99% 的场景是写 patch，不是改源码。这层设计让它极其适合定制——但也埋了本系列最大的坑（见下节）。

3. 工具注册是插件的"副作用"。 插件 apply(ctx, config) 里调 ctx.tools.register(...)，本质是 cordis fiber 上的一个 effect：插件卸载时自动逆序回收，不需要手写任何 dispose。配合每个 model step 都重新 assemble system prompt，工具的热增/热删下一轮自动生效——这就是 live 热更能用的底层原因。

4. 模型看到的工具是"净化过"的。 工具注册表里存着完整 ToolDefinition，但 wire 给模型的 schema 经过白名单过滤，只投 name / description / parameters。output.schema、render 这些是给人/后续处理用的，不进 prompt。这是很干净的信息边界设计。

最值钱的坑：patch 是整值替换，不是深合并
#

地形图里最"反直觉"的一条，来自一个亲手做的实验。

dsh 的 patch 行可以定向覆盖某个插件的 config。文档里它长得很像"合并配置"，直觉上写 config: { maxTitleBytes: 123 } 应该只改这一个键。我拿 base 层的 session-title 插件做实验（它原配置 3 个键），用 --patch 只给 1 个键，然后 --dump-config 对比前后：

# before:config 三键齐全
config:
  fallbackMaxWords: 5
  fallbackMaxBytes: 40
  maxTitleBytes: 80

# after:config 只剩补丁给的 1 键,另两键被清空!
config:
  maxTitleBytes: 123

结论：patch 对目标行是"整 config 值替换"，不是深合并。 想覆盖一个键，必须把整行 config 写全，否则没写的键全部消失。这和源码逐字对应：for (const [key, value] of Object.entries(overrides)) target[key] = value——config 只是被整对象赋值的其中一个字段。

而这个实验还顺带挖出了第二个坑：--dump-config 的输出 ≠ 能 boot。dump 通道是纯离线渲染：不挂载插件、不校验 config schema、连 !!js 都不执行。session-title 的三键在 schema 里全部 required，我那个只给 1 键的补丁如果真实启动必炸，但 dump 照样美滋滋地渲染出"config 只剩 1 键"。所以：判断一个补丁能不能 boot，要看目标插件的 Config schema，而不是看 dump 报不报错。

（好消息是 dump 与 boot 走同一个 applyEntryPatches，所以 dump 永远如实反映 patch 文本层语义——它只是不负责告诉你"这配置活不活得下去"。）

热更机制：live 与 startup 的分叉
#

web profile 之所以能"改完配置立刻生效"，是因为 patchReload: live 时 boot 会挂两个 watchUserPatches（盯 profile 用户层 + home 层两个文件）。文件一变：重读补丁 → entry.update() → 根 Include 事务性重放整叠 patch。失败时保留上一代配置——热更炸了不会把树搞死，这点设计很稳。

代价是什么？我摸到一条有点"惊悚"的结论：生产 profile 默认不挂 logger-console，loader/hmr 的 warn/info 在真实进程里没有输出出口——也就是说"这次热更到底成没成功"，进程内部没有可见信号。行为契约全靠仓库里的 spec 测试兜着。想观测热更结果？得自己挂 exporter。这是定制时值得记住的"可观测性缺口"。

地形图上其他值得记住的铁证
#

  • 会话存储是"单写者 + 内核锁 + fsync + 排他发布"：JSONL.zstd 每帧一次 durable 批写（≤200ms），seq 连续、gap 即 corrupt；读侧只认最高 generation、fail-closed。理解这点，你就不会手贱去改 session 文件。
  • 凭据层叠：env > ~/.dsh/.credentials.yaml > 项目 .env > home .env。 推论很反直觉：想测"缺 key 报错"的路径，清环境变量没用（凭据文件还在），正确姿势是隔离 $DSH_HOME 指向一个空目录。
  • --patch overlay 是"顶不掉"的：live 重组时它固定在用户层之上，你编辑用户层 cordis.patch.yml 永远覆盖不了 --patch 传进去的配置——临时覆盖和持久配置的优先级被刻意分开。
  • 端口 3080 只有一个生效默认：packages/bundle/web-app/cordis.patch.yml 里 webserver 行的 port: !!js ctx.webStartup.port ?? 3080。想改端口可以 --patch 定向 id webserver，但必须连 host 一起 restate（host 是 required 且无默认）——单写 {port: N} 就是上面那个整值替换坑的现场。

地形图的真正用途：扩展点速查表
#

链路图 + 关键文件索引只是"地图"，真正干活靠的是地图背面的扩展点速查表——想做什么，去哪个扩展点，有什么约束：

想做什么入口 / 机制关键约束
加一个工具插件里 ctx.tools.register(defineTool({...}))参数/输出 schema 要全；卸载自动注销
工具按条件出现ctx.inject(['attachments'], …) 条件注册scope 层注册 shadow 全局
加审批门禁tools/pre-execute waterfall 返回 deny决策型扩展点，guard 单调拒绝在 tools/guard
改默认配置patch 定向行 config整 config 值替换——required 键要写全
组合新 profiledsh.profile.bundles 列 bundle 顺序无 bundle 的包只是普通依赖
临时覆盖dsh web --patch <file>overlay 优先级最高，用户层顶不掉
换端口定向 id webserver 改 confighost+port 一起写，别踩整值替换坑

一句话总结这轮摸底：定制 dsh = 往一棵"分层 patch 组装的插件树"里按扩展点插入你的插件；改配置用 patch（写全键），加能力用插件（副作用注册，卸载自动回收）。

摸底之后
#

地形图落盘后，我给自己做了个验收：不看文档，能不能画出从 pnpm dsh web 到工具被模型调用的完整链路、说出每个扩展点去哪改？能。而且这轮摸底直接产出了后续所有工作的"弹药"：

  • 想加工具 → 我知道去哪挂、怎么验证（第 2 篇的插件开发实战）；
  • 想验证但不想花 token / 不想碰真实凭据 → 我知道要隔离 DSH_HOME 接 mock（第 3 篇的无 key 验证闭环）；
  • 想换 UI 皮肤、想包桌面壳 → 我知道 UI 是 web-app bundle 挂的、端口和 host 在哪改（第 4、5 篇）。

读源码这件事，最容易被低估的价值是：它会告诉你哪些路是死的——哪些配置写法必炸、哪些假设不成立、哪些"应该能行"其实文档没写。这些知识写不进官方文档，只能自己踩出来。
